# 对标分析与功能改进建议

> 生成日期:2026-10-25
> 性质:技术路线参考文档(非比赛交付物)。将本项目视为一个**真实的城市内涝 GIS 平台**,
> 对照全球现有洪水/内涝系统(Google Flood Hub、Copernicus EMS、FEMA/USGS、ICEYE、
> 数字孪生水利等)梳理功能差距与改进方向。
> 代码位置引用基于 2026-10 仓库状态(v1.4)。

---

## 一、项目定位确认

**定位:城市内涝(pluvial flood)数字孪生可视化与决策支持平台。**
研究区为广州珠江新城(约 4×4.4 km,`pipeline_config.py:15-16`),双路径建模:

| 路径 | 算法链 | 产物 |
|---|---|---|
| 情景路径 | P-III 设计暴雨(广东查算图表 H24=130mm/Cv=0.40)→ 径流深 → 浴缸法体积注水反演水面高程 W | 2/5/10/50/100 年重现期水深 tif + 淹没 geojson + ±20% 敏感性带 |
| 真实事件路径 | Sentinel-1 RTC + Sentinel-2 五波段 → UNet(GF-FloodNet 训练)水体提取 → 掩膜边界 DEM 中位数反演 W | 英德 2022-06 / 梅州 2024-06 两事件水深与淹没范围 |

### 功能盘点(现状,2026-10 v1.4)

- **三维表达**:CesiumJS 1.95 城市白模(约 1100 栋 Entity 挤出,含楼层带/退台/地标标签/广州塔双曲面拟合)、程序纹理水体(波纹/焦散/岸线泡沫)、24h 三角雨型 8 步演进动画
- **分析能力**:重现期情景、在线模拟(自定义雨量/径流系数)、双屏情景对比、影响统计(建筑/人口/直接损失)、易涝点 Top8、关键设施清单、分区淹没占比
- **应急决策**:四级预警(蓝黄橙红,按淹没面积/分区占比阈值)、A* 避水疏散路径(0.8m 断行)、避难场所、孤岛待援
- **数据产品**:Copernicus EMS 模板专题图三件套(淹没范围/关键设施/危险分级)、水深 XYZ 瓦片(z9–14)、UNet 精度卡、不确定性带
- **公众与社会化**:移动 H5 报汛(拍照上报+分类+管理员核实闭环)、预警邮箱订阅、离线规则问答、用户登录(管理员/公众)
- **工程化**:FastAPI + 可选 PostGIS、Docker 交付、安全加固(频控/XSS 消毒/凭据外置)、pytest 测试体系、CI

"四预"话语体系齐备(预报=情景即输即得、预警=自动分级+订阅、预演=在线模拟+双屏、预案=疏散/避难/设施清单)。

## 二、现状技术盘点(代码级要点)

以下为通读代码后确认的实现方式与短板,是后续改进的事实基础。

### 后端(app.py 等)

- **浴缸法**:`app.py:240-251` 二分 60 次求 W 使陆域 `mean(clip(W−z,0))=q`。无水文/水力模型、无排水、**水面全局强制水平**,河道(z≤0)不参与注水;`pipeline/bathtub_flood.py:90` 的搜索上界与 app 端不一致
- **DTM 近似**:GLO-30 DSM 栅格化 290 栋建筑后 3×3 nan 均值迭代填坑≤500 轮(`bathtub_flood.py:59-84`)
- **水位反演**:掩膜边界像元 DEM 中位数(`water_level_inversion.py:25-35`),DEM 残余建筑会使 W 偏高(梅州事件 DEM 中位差 −245.6m 即例证)
- **损失估算**:`app.py:330-344` 底面积×(高/3.2)×分类型单价(住宅 8500…),损失率 `min(0.85, 0.10+0.28d+0.04d²)` 为自设示例参数
- **疏散 A***:`app.py:1119-1156` 基于格网非路网,8 邻域涉水代价(≥0.8m 阻断/≥0.5m×6/>0.15m×3);BFS 连通域分岛(`1178-1202`)纯 Python 全栅格遍历
- **预警分级**:`app.py:1011-1033` 分区淹没占比 ≥3/8/14/20% → 蓝黄橙红;城市级按淹没面积 0.6/1.0/1.3/1.6 km²
- **实时雨情**:`/api/realtime_rain`(app.py:1603)为**演示假数据**(每 10 分钟轮换情景)
- **存储**:PostGIS 仅两张表(`flood_scenarios` 数值表 + `flood_extent` Polygon+GiST),服务端只用 `ST_AsGeoJSON`,无空间谓词查询;本地优先 GeoTIFF/GeoJSON/JSON 文件
- **工程短板**:每请求新建 psycopg2 连接(无连接池,app.py:162-165);缓存/token 全在进程内存(多 worker 即失效);`_theme_blend` 逐像素 Python 循环(1424-1440)与 `_island_labels` BFS 为 CPU 热点;用户口令 sha256 单轮哈希(store.py:157-158)

### 前端(index.html 等 10 页)

- 建筑白模为静态 JS 数据(web/data/buildings_3d*.js)Entity 挤出,**无 3D Tiles、无 LOD、无合批**;演进动画每步全量重建水体实体
- 水体为 Entity + CallbackProperty 正弦呼吸色 + canvas 程序纹理,**无自定义 shader**;`waterPrimitive` 为声明后从未赋值的死代码(index.html:609)
- 真实事件图层为整幅 PNG `SingleTileImageryProvider`(realevent.html:111-116),未切片
- 仅两处轮询(实时雨情 60s / 报汛上图 120s);token 明文存 localStorage 且 URL 传参(login.html:1741)
- compare.html 为 Canvas 2D 手绘淹没图,非真实地图底

### 算法管线(pipeline/)

- 极值样本为 **5 年"年最大月雨量"** Gumbel 矩法拟合(`prep_return_period.py:74-92`),50/100 年属强外推(代码自注);P-III 设计暴雨(`prep_design_storm.py:26-56`)为权威输入
- UNet:4 层编码-解码,5 波段输入,约 7.8M 参数;BCE+Dice;**场景级(region)划分防泄漏**,但 China 分区 val_IoU≈0.001–0.027(区域不平衡),演示样本 macro IoU=0.738(仅 6 幅)
- 推理含 auto 域适配(逐波段均值偏离 >4σ 切换 instance 归一化,应对 GF-2→Sentinel-2 量级差)
- 真实事件验证:UNet vs SAR 暗像元(VV<0.06)IoU(英德 0.252 / 梅州 0.093)+ 双时相 SAR 变化检测;管线为单时刻快照,无时序演进

## 四、功能改进与新增建议

### A. 模型内核(差距最大、优先级最高)

1. **连通性/填洼法替换全局浴缸法**(改动小、见效快)
   全局单一水平面会产生"高地被淹、低地没淹"伪影。改为逐洼地独立找水平面
   (modified bathtub / depressional storage),只需改 `pipeline/bathtub_flood.py`
   与 `app.py:240-251`,是文献公认的第一步改良。
2. **SWMM 管网耦合**
   城市内涝不算管网是硬伤。学界已有 SWMM+Cesium 成熟范式;可先以简单排水能力
   扣减(按管网密度折算径流系数)过渡,再接真 SWMM 模型。
3. **水动力模型 + DL 代理模型(长期正道)**
   用 HEC-RAS 2D / LISFLOOD-FP 离线跑水动力,以结果为训练对训练深度学习代理模型。
   2025 年 J. Hydrology 研究表明 DL 代理速度可超 GPU 水动力求解器、达近实时——
   本项目已有 UNet 训练基建,顺理成章;`/api/online_sim` 可从"秒级近似"变"真演进",
   24h 演进动画从 8 个静态快照变真实演进场。
4. **设计暴雨方法标准化**
   5 年月值样本换为**广州本地暴雨强度公式 + Chicago 雨型**(国内内涝设计标准做法),
   或 ERA5-Land/逐日站点资料,消除 50/100 年强外推。
5. **集合不确定性**
   ±20% 敏感性升级为多参数集合预报(GloFAS 核心),前端紫色水体图层天然适合展示集合包络。

### B. 数据底板(对标 L1/L2/L3)

6. **三维资产 3D Tiles 化**
   建筑转 batched 3D Tiles + 要素属性,获得 LOD 与十万栋级扩展能力;
   真实事件整幅 PNG 换 COG 或 PMTiles 切片;清理 `waterPrimitive` 死代码。
7. **精细地形与地下空间**
   GLO-30 30m 是水深精度瓶颈(水位反演误差已观察到)。可上 LiDAR DTM / 广州实景三维;
   下穿隧道、地下车库等负空间恰是内涝最致命场所,值得做 L3 级专题。
8. **OGC 标准化发布**
   OGC API – Features/Maps + COG/PMTiles,让 QGIS/ArcGIS 可直接消费——
   真实 GIS 平台的生命线是互操作,这是"比赛项目"最容易忽视的一层。

### C. 实时化与预报链条(从演示到可用)

9. **接入真实雨情(分水岭级改进)**
   `/api/realtime_rain` 目前是假数据。接入 GPM IMERG 早实时、气象雷达 QPE 或区域
   自动站后,实时雨情卡、预警条、大屏即成真系统。
10. **天气预报驱动管线**
    GFS/ECMWF 降雨预报 → 浴缸法/代理模型 → 未来 24–72h 内涝风险图,
    使"预报"从话语变成事实(Google Flood Hub 模式)。
11. **IoT 传感器网络接口**
    预留水位计/电子水尺/路口摄像头 AI 识别接入;预警分级从淹没面积阈值升级为
    多站点实测水位 + 雨量指标融合(FIMAN 模式)。
12. **Sentinel-1 自动化消费**
    STAC 轮询自动检测新过境影像并触发 realevent 管线;GFM 全球淹没开放产品可作验证源。

### D. 决策支持深化

13. **单点水淹过程线(hydrograph)**
    水动力化后给每个可点击点出"何时开始淹/水深过程/何时退水"时间曲线——
    真实系统最核心的决策信息,当前只有瞬时快照。
14. **工程预案情景库**
    compare.html 目前仅支持径流系数 C 切换。真实的"预演"支持泵站强排、调蓄池、
    河涌预泄、管网改造等方案——在 DEM/排水参数上局部修改后真正重算,构成方案比选。
15. **损失模型标准化**
    自设损失率曲线换为国内《洪灾直接经济损失评估》分行业曲线或 HAZUS
    depth-damage 曲线(分建筑结构类型)。
16. **网络型关键设施与连锁失效**
    关键设施从"被淹清单"升级为电网/通信/路网拓扑分析(某变电站被淹 → 影响片区 →
    医院备用电源可持续时间)。
17. **智能问答升级 LLM function-calling**
    规则引擎保留兜底,上层接 LLM 把 26 个 API 端点当工具调用,可问范围质变。

### E. 平台工程与可信度

18. **性能与部署健壮性**
    psycopg2 连接池 + Redis/文件缓存(消除多 worker 失效)+ `_theme_blend`/
    岛屿检测 numpy 向量化;支撑真实并发。
19. **鉴权现代化**
    sha256 单轮 → bcrypt/argon2;内存 uuid token → 持久化 JWT;
    `FLOOD_DOCS=1` 的 OpenAPI 扶正为正式开发者入口。
20. **公众报汛反哺模型(公民科学闭环)**
    报汛照片含参照物可半自动反演水深,作为高水位标记用于率定/验证淹没模型——
    前沿研究热点,让报汛模块产生科学价值而不只是交互功能。
21. **触达渠道扩展**
    订阅目前仅邮箱登记;补企业微信/钉钉 webhook、短信网关等真实触达。

## 五、优先级路线图

| 优先级 | 事项 | 理由 |
|---|---|---|
| 1 | 连通性/填洼法替换全局 bathtub | 改动小,可视化伪影立刻消失,可信度直接提升 |
| 2 | 3D Tiles 化 + 水体 shader 化 | 性能与观感双重跃升,数字孪生标准资产 |
| 3 | 真实雨情接入 + 预报驱动管线 | "演示"→"可用"的分水岭 |
| 4 | SWMM 耦合 → DL 代理水动力 | 模型内核长期正道,复用已有 UNet 基建 |
| 5 | OGC 发布 + 单点过程线 + 工程预案库 | 互操作与决策深度,真实系统依赖项 |

**一句话总结**:本项目当前强项是**可视化表达与产品完整度**(已不输多数真实系统),
短板集中在**水动力内核的真实性**与**数据链路的实时性**——恰好也是 Google Flood Hub、
Copernicus、FIMAN、ICEYE 等标杆系统投入最重的地方。
